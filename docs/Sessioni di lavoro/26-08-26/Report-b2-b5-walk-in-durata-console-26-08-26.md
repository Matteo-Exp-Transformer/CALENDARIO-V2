# Report B2+B5 — walk-in senza limite separato e durata base da console

**Data:** 26-08-2026 · **Branch:** `env/test` · **Ambiente:** repository locale; e2e mutante eseguito solo su TEST `docnnernvp` con setup e cleanup prefissati; nessuna operazione PROD
**Modalità:** deep · Esecuzione catena seriale B2 → B5

## 1. Cappello

- **Cosa è cambiato:** in Servizio il walk-in non ha più un tetto coperti separato e una nuova prenotazione admin usa la durata base impostata in Console per calcolare la fine effettiva, verificabile a `inizio + 90 minuti` con il default.
- **Cosa resta:** le due manopole `table_late_threshold_minutes` e `table_release_notice_recall_minutes` restano da decidere con Matteo; il doppio turno attivo sullo stesso tavolo è fuori cantiere.
- **Serve una tua azione:** sì, il ritest manuale B2+B5 descritto al §10; nessuna migrazione né azione DB da applicare.

## 2. Intervento eseguito

1. Rimosso `walk_in_max_guests` dai registri app e Console, dall’interfaccia Servizio e dalla pagina Console: non esiste più la card “massimo coperti walk-in”. La capienza della fascia resta un avviso ambra, confermabile al secondo click.
2. Aggiunto `restaurant_default_duration` nei due registri: intero con default 90 e intervallo 30–360 minuti. La Console lo mostra tra le impostazioni intere esposte.
3. La creazione admin risolve prima la durata con `resolveBookingDuration`, poi calcola `confirmed_end` in minuti interi e salva lo snapshot della stessa decisione. Per 90 minuti non usa più il vecchio finale implicito a tre ore; anche 31 minuti resta esattamente `+31`, non un'approssimazione in ore frazionarie.
4. Il walk-in passa la medesima durata base al resolver, così il controllo capienza osserva la stessa finestra che verrà salvata.
5. Integrato B3 V3 nei documenti d’area e in `FOLLOW_UP`: duplicato prima dell’overlap, messaggio con entrambi gli intervalli, label coperti completa.

### 4-bis. Fail procedurale MSS e ripresa

`npm run validate:mss:all` è uscito `1` nel sottopasso `npm run test:mss:tools`: al primo run `V1`, `D14` e `T13/lavagna` hanno segnalato viste generate non allineate agli owner/ai nuovi report presenti nel working tree. Non è un fail del codice prodotto né una capsula negata; la causa procedurale era la mancata rigenerazione delle viste dopo la creazione dei report B2+B5 e B3. Ripresa eseguita: `npm run generate:mss:views` e `npm run validate:mss:views` sono verdi.

Il rerun di `npm run test:mss:tools` ha individuato un secondo difetto reale di manutenzione del controllo: il test T13 legge l’owner vivo `PLAN_V0.md`, ma conservava l’aspettativa della fase precedente (`WP-1` `NON INIZIATO` → `da-fare`). L’owner oggi dichiara legittimamente `WP-1` **IN PILOTA — ombra**. Correzione: la vecchia stringa NO-GO resta una fixture esplicita contro il falso `PASS`, mentre il controllo live ora pretende `IN PILOTA`, bucket `non-classificata` e assenza dalla colonna “Fatte”. Non sono stati modificati `PLAN_V0.md`, stato `WP-1`, cutover o regole di classificazione: è stata corretta soltanto la semantica del test rispetto all’owner. Dopo `npm run generate:mss:views`, `npm run test:mss:tools` e `npm run validate:mss:all` sono verdi.

**Complicazione strumenti/MSS e soluzione:** i report nuovi rendono volutamente stale l’indice generato; il primo giro ha quindi esposto tre sintomi insieme (due viste stale e il test T13). Il generatore non è un rumore: ha bloccato una vista che non rappresentava più il filesystem. La soluzione è stata prima rigenerare tutte le viste con il comando owner-aware, poi distinguere l’incoerenza residua del test dall’owner. Questo conferma due limiti operativi da mantenere visibili nel MSS: (a) aggiungere un `Report-*.md` richiede sempre rigenerazione dell’indice prima del gate; (b) i test che leggono owner vivi non devono codificare uno stato transitorio, ma devono verificare il bucket e l’invariante di prodotto/sistema. Nessun tool MSS è stato allentato e nessun esito è stato mascherato.

**Addendum orchestratore — E2E Pro (26-08-26):** i primi due run completi avevano 12/13 pass: il solo scenario walk-in alternava il punto della doppia conferma perché il tenant TEST poteva attivare contemporaneamente l'avviso di capienza. Correzione del *setup*, non dell'asserzione: lo scenario salva e imposta temporaneamente `table_mode_respects_slot_cap = false`, verifica esplicitamente l'assenza di `capacity-warning`, poi ripristina lo snapshot nel `finally`. Il test torna quindi a esercitare solo occupato → cambio sala → occupato → doppio click e passa **1/1**. Non sono stati modificati il copy né i rami di forzatura del prodotto.
